# v0.6.39 Quick Checkout, Inventory Navigation, and Technician Identity Design

## Goal

Improve three existing POS workflows without changing their underlying business rules:

1. Close Quick Checkout automatically after a successful checkout.
2. Make inventory parents and variants faster to manage and make device-based part lookup more direct.
3. Add synchronized, selectable technician profile icons throughout the live POS interface and use them to organize Daily Look tasks.

The release must preserve all unrelated behavior, remain usable on desktop and mobile, and must not add profile icons to customer-facing printouts.

## Scope and Boundaries

This release extends existing components, persistence, and context-menu conventions. It does not introduce a new technician table, change ticket assignment identity, redesign inventory storage, or alter print templates.

“Parent categories” in the inventory request means the existing green Parent Part rows. Device and Part Category headings remain navigational headings and do not gain destructive context actions.

## Quick Checkout Completion

After the existing Quick Checkout workflow completes successfully—including persistence, inventory consumption, and any selected receipt action—the Quick Checkout window closes automatically. The close happens for every successful completion rather than only when the current `closeParent` result flag is set.

The window remains open when validation fails, checkout persistence fails, inventory processing fails in a way the existing flow treats as fatal, or the user cancels. Existing error messages and retry behavior remain available.

## Inventory Context Actions

Inventory uses the established `ContextMenu` and `useContextMenu` patterns. Desktop users open actions with right-click. Mobile users use the existing long-press-to-context-menu bridge.

### Parent Part actions

- Edit Parent Part
- Add Variant
- Expand or Collapse Variants, reflecting the current row state
- Delete Parent Part, using the existing protected/confirmed deletion behavior so linked data is not silently lost

### Variant actions

- Edit Variant
- Duplicate Variant, opening or creating an editable copy through the existing inventory persistence path
- Print Label, reusing the current inventory label preview and print flow
- Delete Variant, with explicit confirmation and existing linked-record protections

Actions operate on the selected row and preserve the current editor’s full capabilities. Buttons already available elsewhere remain unchanged unless duplication is unnecessary for the context-menu entry point.

## Device-Priority Inventory Search

The existing search input continues to match normal inventory metadata. When the entered query resolves to a device name, the result presentation prioritizes that device:

- Exact normalized device-name matches show that device group rather than unrelated groups.
- Matching device groups open automatically to reveal their part categories and parent parts.
- Generic searches still search the current supported fields and show all relevant results.
- Selecting a result opens the same full inventory editor used today; search does not create a simplified or read-only editing path.

Device grouping continues to reference shared inventory records. It does not clone quantities or variants per device.

## Technician Profile Icon Model

Add one nullable icon identifier to the existing `staff_profiles` record and the corresponding local `Technician` model. The value is a stable identifier from a fixed application-owned icon catalog, not arbitrary SVG, markup, or an external URL.

Desktop and mobile serializers read and write the field through their existing technician synchronization paths. Existing Supabase realtime subscription behavior carries profile changes across active POS sessions. Tickets continue storing technician assignment by their current identity fields; icon rendering resolves against the latest technician profile at display time. Therefore, changing an icon updates both past and future ticket displays without rewriting ticket history.

If a technician has no icon or an obsolete identifier, the interface shows a neutral default avatar. The schema change is additive and nullable.

## Technician Icon Placement

Icons are application-only visual identity and must never appear on printouts.

- Work orders, sales, and consultations show the assigned technician’s icon beside the Assigned To control near the top of the form.
- Main-screen tables show a small icon beside the technician name in assigned-technician columns.
- Missing or unresolved technicians use the neutral default without disrupting the name or layout.
- Responsive layouts keep the icon compact and do not force labels, dates, or time values onto avoidable extra lines.

## Daily Look Task Presentation

Daily Look replaces the plain per-technician task list entry point with a responsive technician avatar row:

- Each technician icon has a prominent numeric badge containing that technician’s open task count.
- Clicking or tapping an icon selects that technician and reveals their tasks using the existing task interactions and completion behavior.
- A zero-task technician remains visible but uses a visually quiet zero/empty state.
- Tasks assigned to `All Technicians` appear below the avatar row as a compact, slightly overlapping stack, clearly separated from individually assigned tasks.
- The layout wraps or horizontally scrolls as appropriate on narrow screens while preserving tap targets and readable badges.

Task ownership and persistence do not change. This is a new presentation and filtering layer over the existing Daily Look task data.

## Error Handling and Compatibility

- Unknown icon identifiers fall back safely rather than blocking technician or ticket rendering.
- Technician saves retain the current validation and surface sync failures through existing error/toast conventions.
- Inventory delete actions require confirmation and respect linked-record constraints.
- Search with no matches shows the existing empty state and does not mutate expansion state permanently.
- Quick Checkout closes only after the success path has finished.
- Desktop right-click and mobile long-press invoke equivalent inventory actions.
- Existing persisted technicians without an icon continue to load normally.

## Supabase Migration

Use the installed Supabase CLI’s discovered commands to create an additive migration for the nullable technician icon identifier on `public.staff_profiles`. Do not add a new table, broaden RLS policies, or expose new user-controlled markup. Verify local migration ordering and, where the configured project permits, verify the applied column and run database advisors. The existing grants, RLS, and realtime publication for `staff_profiles` remain in force.

## Testing and Verification

Implementation follows test-driven development. Focused tests must first demonstrate the missing behavior and then cover:

- Quick Checkout closes after success and remains open after failure/cancellation.
- Inventory parent and variant menus expose the correct actions and act on the correct record.
- Device-name search prioritizes and expands the matching device without breaking generic search.
- Icon catalog contains exactly the approved 25 unique identifiers grouped 10/5/5/5, and unknown identifiers fall back safely.
- Technician serialization round-trips the icon on desktop and mobile.
- Assigned-technician displays resolve the current profile icon on ticket forms and main tables.
- Daily Look badges count open tasks correctly, technician selection filters correctly, and all-technician tasks render separately.
- Print models/templates remain free of technician profile icons.

Run the repository’s focused tests, full test suite where practical, renderer and Electron typechecks, lint, desktop build, mobile/web build, and Windows packaging workflow used by prior releases.
